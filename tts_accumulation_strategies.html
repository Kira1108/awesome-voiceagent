语音 AI 代理 TTS 文本聚合策略分析

深度解析 Pipecat 与 LiveKit 的流式文本处理机制

在语音 AI 代理中，LLM 输出的文本通常是以“流（Stream）”的形式产生的。为了让生成的语音听起来自然且连贯，不能每收到一个词就发给 TTS，而需要一套文本聚合策略。以下是业界两大主流框架的深度对比。

1. Pipecat 的策略：基于 NLTK 的智能分句

Pipecat 主要通过 SentenceAggregator 处理器来实现，侧重于利用自然语言处理工具包（NLTK）进行高精度的句子边界检测。

核心逻辑：
  • NLTK 驱动：使用 nltk.tokenize.sent_tokenize。这是一个成熟的 NLP 库，能识别复杂的句子边界（例如能区分 Mr. 中的点和句尾的点）。
  • 标点符号过滤：维护了一个庞大的标点集 SENTENCE_ENDING_PUNCTUATION。
  • 兜底逻辑：如果 NLTK 返回了多个句子，它会立即把第一个句子推送给 TTS。如果只有一个句子，它会检查最后一个字符是否在标点集中。
关键实现路径：
pipecat/src/pipecat/processors/aggregators/sentence.py
class SentenceAggregator(FrameProcessor):
    async def process_frame(self, frame, direction):
        # ... 累积文本 ...
        if isinstance(frame, TextFrame):
            self._aggregation += frame.text
            # 调用智能分句判断
            if match_endofsentence(self._aggregation):
                await self.push_frame(TextFrame(self._aggregation))
                self._aggregation = ""
标点检测工具：
pipecat/src/pipecat/utils/string.py
# 覆盖了拉丁语、东亚语（中日韩）、印度语、阿拉伯语等
SENTENCE_ENDING_PUNCTUATION = frozenset({
    ".", "!", "?", "。", "？", "！", "；", "…"
})

def match_endofsentence(text: str) -> int:
    sentences = sent_tokenize(text) # NLTK 分句
    if len(sentences) > 1:
        return len(sentences[0])
    # 针对单句进行标点校验
    if text[-1] in SENTENCE_ENDING_PUNCTUATION:
        return len(text)

2. LiveKit 的策略：正则匹配与长度控制

LiveKit 采用了一套更轻量级但更精细的正则表达式规则，特别强调通过最小长度控制来优化听感。

核心逻辑：
  • 正则表达式预处理：定义了大量 Regex 规则来处理 Mr.、.com、Ph.D. 等特殊情况，防止误切分。
  • 最小长度限制 (min_sentence_len)：默认设为 20 个字符。即便收到了标点，如果长度不足 20，也会继续等待，避免语音过于细碎。
  • 格式处理：支持保留换行符（作为自然停顿）或将其替换为空格。
关键实现路径：
agents/livekit-agents/livekit/agents/tokenize/_basic_sent.py
def split_sentences(text: str, min_sentence_len: int = 20):
    # 1. 规则化处理特殊缩写
    text = re.sub(prefixes, "\\1<prd>", text)
    # 2. 标记真正的句尾
    text = re.sub(r"([.!?。！？])([\"”])", "\\1\\2<stop>", text)
    
    splitted_sentences = text.split("<stop>")
    sentences = []
    buff = ""
    
    for match in splitted_sentences:
        buff += match
        # 关键点：长度控制，只有超过阈值才视为独立句子推送
        if len(buff) > min_sentence_len:
            sentences.append(buff)
            buff = ""
    return sentences

4. 共同的通用流程

  1. Buffer 累积：将 LLM 吐出的 Token 拼接进一个字符串缓存。
  2. 句尾扫描：每收到一个新 Token，扫描 Buffer 尾部是否匹配“分句标点”。
  3. 合法性校验：确认标点不是缩写的一部分（如 e.g.）。
  4. 推送 TTS：一旦确认是一句完整的话，将该段文本推送到 TTS 合成队列。
  5. 尾部处理：当 LLM 流结束（End Frame）时，强制推送 Buffer 中剩余的所有文字。

注：这种策略平衡了 首包延迟（Latency） 和 语音自然度（Prosody）。

5. 进阶探讨：TTFA 与解码耗时的终极权衡

在实际生产环境中，如果仅按照“20字符或句号”聚合，考虑到 LLM 典型的解码速度（如 20 字/秒），仅等待生成 20 个字就需要 1 秒钟。加上 TTFT (Time To First Token) 和 TTS 合成时间，用户感知到的 TTFA (首音延迟) 将达到不可接受的 1.5 秒以上。

为了解决这一痛点，工业界通常采用 “不对称分句（Asymmetric Chunking）” 与 “掩盖延迟（Latency Hiding）” 的高级策略：

核心策略：首句极速，后句求稳
  • 第一句话（首包）极速切分： 只要遇到第一个标点（即使是逗号），或字符数达到 3~5 个，立即送给 TTS。这样将首音延迟压缩至极致（约 600-700ms）。
  • 后续句子恢复长句切分： 利用 TTS 朗读第一句话的“播放时间”（通常 0.5-1 秒左右），来掩盖 LLM 后续生成的“解码时间”。后续文本恢复“等句号或长逗号”策略，以保证语音自然度。
代码实现示例（不对称分句）：
global is_first_chunk = True # 每次用户说完话重置为 True

def should_trigger_tts(buffer_text, current_char):
    global is_first_chunk
    
    if is_first_chunk:
        # 首句策略：见短标点就发，或超 5 个字强制发
        if current_char in ("，", "。", "！", "？", "：") or len(buffer_text) >= 5:
            is_first_chunk = False
            return True
        return False
        
    else:
        # 后续策略：认句号，或长于 18 个字的逗号
        if current_char in ("。", "！", "？", "\n"):
            return True
        if current_char in ("，", "；") and len(buffer_text) > 18:
            return True
        return False

配套的架构级优化：

  • 提示词工程 (Prompt Hack)： 强制 LLM 养成先说短语的习惯。在 System Prompt 中加入：“你必须使用口语化的中文回复。每次回答的前几个字必须是简短的语气词或确认短语，并紧跟一个逗号（例如：'好的，'、'明白，'）。”
  • 真·流式 TTS 引擎 (True Streaming TTS)： 对于极度苛刻的延迟要求，改用支持 WebSocket 级别流式输入（逐字输入）的 TTS（如 Cartesia、ElevenLabs、基于流式框架魔改的 CosyVoice）。这类引擎内部维护声学缓冲区，一边接收单字，一边预测语调并出声，无需在业务层手动做粗粒度的 split。
